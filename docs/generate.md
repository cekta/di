# Генерация контейнера

`cekta/di` для своей работы имеет два этапа:

1. **Генерация контейнера**.
2. [Использование сгенерированного контейнера](usage).

Во время генерации контейнера строится карта зависимостей на основе [Manifest](manifest), а также разрешаются все указанные сущности.

Если генерация завершилась успешно, запоминаются используемые параметры для разрешения всех зависимостей, и в дальнейшем их необходимо будет передавать.

Например, если для подключения к БД использовался параметр `dsn`, то после генерации изменённый `manifest` без этого параметра приведёт к тому, что подключение к БД не сможет создаться, и все зависимости от него тоже.
Поэтому всё, что использовалось при генерации, должно передаваться в дальнейшем, это отслеживается.

Процесс генерации является ресурсоёмким, однако после него зависимости разрешаются максимально быстро и оптимизированно.

> После изменения исходного кода (зависимостей) необходимо повторно генерировать контейнер, чтобы обновить зависимости.

## Генерация с ContainerGenerator

Для генерации класса контейнера используется [ContainerGenerator](https://github.com/cekta/di/blob/master/src/ContainerGenerator.php), который принимает [manifest](manifest) в качестве конфигурации.

**bin/generate.php**

```php
<?php
declare(strict_types=1);

require_once __DIR__ . '/../vendor/autoload.php';

$manifest = new \App\Manifest();
$generator = new \Cekta\DI\ContainerGenerator();
file_put_contents($manifest->filename(), $generator->generate($manifest));
echo "{$manifest->filename()} was generated" . PHP_EOL;
```

Использование:

```bash
php bin/generate.php
```

Например, во время разработки, когда вы закончили изменять файлы, перед проверкой можно запустить такой скрипт, а затем проверить внесённые изменения.

Также скрипт полезен при сборке (build) релиза, чтобы собирать его единожды рядом с `composer install`.

Любые попытки оптимизировать запуск генерации:

1. Генерация в runtime при первом обращении.
2. Наблюдение за изменением файлов в проекте (watch-режим, как в JS-проектах).
3. Подсчёт контрольной суммы.
4. Подписка на событие `composer install` и запуск сразу после.

> Все эти способы имели различные недостатки. Запуск скрипта вручную оказался самым простым, надёжным и однозначным решением.

## Генерация с ContainerFactory

### Когда нет файла контейнера

[ContainerFactory](https://github.com/cekta/di/blob/master/src/ContainerFactory.php) генерирует файл контейнера, но делает это только в том случае, **если файла нет** (не обновляет существующий).

[Пример подробно описан в начале работы, при этом можно пропустить пункт 3](start).

Это полезно для разработчиков, которые только склонировали проект и запускают его в первый раз. Не стоит использовать это в релизах.

### forceRecreate

Позволяет генерировать файл контейнера каждый раз как его пытаются создать с помощью `ContainerFactory`.

**index.php**

```php
<?php
declare(strict_types=1);

require_once __DIR__ . '/../vendor/autoload.php';

$factory = new \Cekta\DI\ContainerFactory();
$container = $factory->create(
    manifest: new \App\Manifest(), 
    forceRecreate: (bool)(getenv()['APP_RECREATE'] ?? false)
);

$example = $container->get(\App\Example::class);
$example->payload();
```

Пример использования:

```bash
export APP_RECREATE=true
php index.php
```

Установив переменную окружения, вы заставите каждый вызов генерировать новую версию контейнера. 

> Такой подход — **только** для разработки и имеет накладные расходы около 100 мс на каждый запрос (время на генерацию контейнера).
